Twenty Instruments, Still Failing

Twenty gates, boards and checks were built against those four classes in thirty days, and the work has not got smoother. This document exists to ask why, not to record that they were built. The counts below are the beginning of an answer, and they point somewhere other than effort.

What the counts say

Four measurements, taken today across every local repository. Each one was a surprise, and together they explain a workload that feels like it is not converging — because it isn’t.

14/20

live in exactly one repository. Only six instruments ever travelled to a second project. The estate is not accumulating a toolkit; individual repositories are.

1

instrument inherited by the newest project. This repository is six days old. It arrived with the heredoc gate and built twelve more of its own from its own failures — re-deriving, not inheriting.

20/20

gate a failure that had already happened. Read the origins below: every one names a specific past incident and blocks exactly that. None generalizes. Known failures stop recurring; novel ones are not slowed at all.

25×

more commits per month since July 2026 in the repository that spans the change — 30–45 a month for two years, then 885, then 1,042. Twenty instruments against that is not convergence. It is running to stand still.

Put together, those four are a mechanism rather than four complaints. Throughput rose twenty-five-fold. Each instrument retires exactly one known failure and does not travel. New projects start near zero and re-derive. So the rate of novel incidents tracks the volume of new work, and the volume of new work went up — which is precisely the experience of building tools all month and generating cases every day at the end of it.

What this does not say. It does not say the instruments failed. Each one demonstrably retired its own failure, and the six that travelled retired it in up to seven places at once. The complaint is not that they do not work. It is that working is not the same as compounding, and nothing here compounds yet.

What this document is for, and what would settle it. Four questions, in the order the counts raise them. None is answered here, and the first two are the ones most worth an outside opinion.

  1. Why does the toolkit not travel? Six of twenty spread; fourteen did not. The six that did all fire automatically. Is the barrier that the rest need invoking — or is it that vendoring is manual, with a registration step in two places and no package to install?
  2. Should a new project inherit a baseline at all? The newest repository arrived with one instrument and built twelve. If those twelve were genuinely project-specific, that is correct and there is nothing to fix. If half were re-derivations of instruments that already existed elsewhere, that half is the whole complaint. This document does not yet distinguish the two, and doing so is one afternoon’s work.
  3. Is a per-incident gate the right unit? Every instrument here retires exactly one known failure. Nothing anticipates a class. Twenty specific gates against rising throughput may simply be the wrong shape of answer.
  4. What is the actual incident rate, and is it falling? Not answerable from this repository — it is six days old and its case files are dominated by one afternoon’s batch. A longer-running project would answer it; this one cannot, and saying so is more useful than a trend drawn through six points.

Method. Counted 2026-09-01 across eighteen local repositories with find, git rev-list, git log --diff-filter=A and git branch --no-merged. Origin failures are quoted or condensed from each tool’s own header comment, which is where this estate records them; nothing is reconstructed from memory. Duplicate hits from -worktrees checkouts are collapsed, so a count is repositories rather than working copies.

Dates are first-appearance, not authorship. All twenty entered git between 2026-08-01 and 2026-08-30. For a vendored tool that is when the copy arrived in that repository, so several are older upstream than they look here.

What was excluded, and the criterion. One repository carries ninety files under tools/; most are analysis and figure scripts and are not instruments in this sense. The line drawn is: does it check, gate, coordinate or retrieve? Analysis code that produces a result is out; a script whose whole job is to notice something is in. That is a judgement, and a different one would change the count of twenty.

Not verified. These headers were read, not run. No selftest was executed for this table, and mutation_check.sh exists precisely because a green selftest has already turned out to prove nothing here. Dates are as each tool states them; a tool that misdates its own origin carries the error straight into this page.

Also not shown: what any of it failed to catch. Unmerged branches across these repositories run from 14% to 88%, and no instrument in this document addresses branch hygiene at all.
