Onboarding strategy · draft for review

Before the First Data File

Bringing a new faculty member onto agentic work, sequenced by dependency rather than by topic — and deferring every guard until something has gone wrong to justify it.

The window, and what closes it

A new faculty member is the only person for whom this is free. Everyone else is retrofitting — writing a path helper around scripts that already hardcode paths, adding a remote to a repo with ninety commits in it, deciding which storage holds what after the disk has filled.

The window opens on the start date and closes at the first data file. It is measured in weeks, and nothing announces its closing.

Two of the steps below are impossible to do late rather than merely expensive. A commit hook stamping agent authorship cannot be applied retroactively — a repo that adds one on day sixty has to say assume agent authorship unless a commit says otherwise for everything before it, which is a permanent hole in its own record. A born-on date works the same way: derived once, or typed forever after.

Everything else on this list is cheap now and archaeology later. That asymmetry is the entire argument for doing it at onboarding instead of when it hurts.

What they are being onboarded onto

The distinction this course exists to teach is one the university already enforces at the level of who gets an account. A new faculty appointment crosses that line on its start date.

It also means the new hire arrives in the exact population that has the agent and has been offered no instruction in it.

The rules this plan runs on

Stated first so the sequence reads as consequences rather than as tips. These are simultaneous constraints, not stages.

  • One thing at a time. One change, verify, commit, next. You cannot tell what broke if you changed four things.
  • Spec, validate, re-spec — and re-spec is the normal case. Not the exception, not a sign of a bad prompt. A person who never re-specs is accepting first output.
  • Guards are built only from friction. Every guard worth having exists because something specific went wrong first. Building them up front is the asymptote with extra steps.
  • A request is not a rule. An instructions file is not enforceable. Use all the bad words you like; the second sentence is still skipped.
  • The repo is a record, not undo. What happened and why — including what did not work, which stays in the history rather than being edited away.

The sequence

Ordered by dependency: each layer can only be verified once the one below it exists. One thing runs the other way — the items involving people who are not you take longest, so they start first and finish last.

A Before the start date gated on other people · days to weeks
  1. 1 Ask the department for a Shortcode — and ask what caps it. For most faculty this is an unasked question rather than an ineligibility. Without one, the Toolkit, Claude Code and classroom provisioning are all blocked in a single stroke.
  2. 2 Decide whether research storage or HPC applies at all. Most people need neither — a laptop, synced storage and one repo covers the majority of research computing. Knowing which side of that line you are on is the decision, and it is worth minutes now against weeks of approval later.
  3. 3 Answer the two branch questions: more than one machine? solo or team? These are asked at the door rather than discovered in week three, because they change what the rest of this has to cover. A solo researcher on one laptop drops most of phases A and D — a much shorter onboarding.
B Identity, before any code exists hours
  1. 4 GitHub account, SSH key, gh auth login. A remote exists from the first hour, which is what makes step 12 possible rather than a migration.
  2. 5 Claude Code via the Toolkit — the moment eligibility begins. This is where the cost question stops being abstract. See the caution below; for a faculty member it is the one thing that is worse than it is for a student.
  3. 6 Institutional basics: login, VPN client, synced-storage client.
C Machine baseline one sitting
  1. 7 Package manager, then git, gh, node, ripgrep, jq.
  2. 8 VS Code and the agent extension.
  3. 9 One language runtime. Only the ones you need. Most people need one.
  4. 10 Stop the machine sleeping through its own work. A session or an analysis run that outlasts your attention dies when the lid closes, and it dies without a result. caffeinate -dimsu is built in and needs no install. A good share of the people who think they need a cluster need this instead — try it before filing a requisition that takes weeks.
D Decisions that are free now before the first data file
  1. 11 Write the storage tier rule down. Three sentences. Which class of storage holds what. It prevents both failures at once: multi-gigabyte outputs strangling a sync client, and small shareable results stranded where the other machine cannot see them.
  2. 12 Write the path helper before any script hardcodes a path. Cheap now, archaeology later. A sibling project carries a stale path island it describes in its own words as rooted somewhere nothing else uses — flagged for cleanup, still not fixed.
  3. 13 git init and add the remote in the same sitting.
  4. 14 Ignore data by extension; pin eol=lf on shell scripts. A carriage return in a shebang is a bad interpreter failure on a Linux cluster, and it is a genuinely awful thing to debug from a Windows checkout.
  5. 15 A commit hook stamping agent authorship. The one item on this page that is impossible late rather than expensive. Add it on day sixty and every earlier commit is permanently ambiguous about who wrote it.
E First contact, which contains a deliberate failure week one of real work
  1. 16 The bake-off: the same request to search, to chat, and to the agent. Shows the escalation instead of asserting it. Search returns links and you do the work; chat returns text and you decide what to do with it; the agent acts on your filesystem. It starts from the one tool everyone has already used, and it opens with the machine being wrong rather than with reassurance.
  2. 17 One real task from their own work, small, with a validation step named in advance. Four checks that need no code: read the diff for scope rather than correctness, run it and look, list the files that now exist, open the artifact yourself. Name which one applies before the task runs, or it will not happen.
F The guard layer deliberately empty
  1. 18 Nothing. On purpose. No hooks, no session-start briefing, no checks configured in advance. Every guard is built later, from a specific thing that went wrong, on a date. The evidence for this sits in our own history: a session-start briefing grew until it killed sessions outright, and the fix was architectural rather than tuning. Building the guard layer during onboarding is the most legible way to fail this course while appearing to take it seriously.

The faculty-specific danger

Uncapped spend

A personal plan makes the plan the allotment — a ceiling you hit. That is the case our material assumes throughout. The institutional path inverts it. Claude Code is billed at list per-token rates against a departmental Shortcode, uncapped: nothing stops, nothing warns, and the number surfaces when somebody else reads the monthly statement.

In the course's own terms — a ceiling is a crude mechanism, but it is a mechanism. A Shortcode is a request that the spender be sensible, and this whole course is about what happens to requests. A new faculty member is the first person in our audience to be handed the uncapped case on day one, and it is the part of our material that does not yet cover them.

How we would know it worked

Confidence is not the measure; a person who is confident after week one has usually skipped the validation. These are observable in the repo.

  • They have re-specced at least once without being prompted to.
  • They can say what the agent did without reading the code — by scope of diff, by files that now exist, by opening the artifact.
  • The repo contains at least one commit recording something that did not work.
  • Their first guard, whenever it appears, points at a specific dated failure.
  • A polished session-start script exists by week two. That is the asymptote, arrived early.
  • The instructions file has grown past a page and is being edited in place of changing the workflow. That is a request being mistaken for a rule.

What is unverified here

This document would fail its own course if it presented itself as finished, so:

Nobody has been onboarded this way. Zero runs. The order is derived from what our own retrofits cost us, which is evidence about what went wrong — not evidence that this sequence prevents it.

The access table was checked on 27 August 2026 and is eight days old at the time of writing. Our own note on it says to go touch the systems rather than edit around the dates. That has not been done for this draft.

The no-Shortcode precedent is single-source. The pricing page offers a no-cost faculty tier for one service, which suggests ITS already runs tiers that do not require a Shortcode. It was read once and not confirmed on a second page. It is the most decision-relevant line here and the least verified.

No cost figure applies to this case. The one concrete number we have — roughly five to fifteen dollars a student for a ninety-minute session — is an estimate rather than a measurement, and it describes a capped student account. A faculty member on an uncapped Shortcode doing daily work is a different question, and nobody has measured it.

The phase labels are dependencies, not durations. "Week one" means after the thing below it exists. No one has timed any of this.
