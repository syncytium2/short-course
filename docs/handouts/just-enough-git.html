Just Enough Git

Enough to read what your agent tells you it did — what git is for, the dozen words, and why keeping a repository tidy is a job you can hand over rather than learn.

You do not have to learn git, and you are not going to be graded on it. Running it is something a coding agent does well, and on the browser route in Cold Start you never type a command at all. What you cannot hand over is reading the report — because it comes back in these words, and a report you cannot read is not a report. That is what this page is for, and it is a smaller job than learning git.

What it is for

Git keeps every version of your work, and a note about why each one changed. Not the last version — all of them. You can go back to any of them, and you can ask what the state of things was on a particular day.

That is the whole idea. Everything else is machinery for doing it without thinking about it.

The one thing worth understanding before any of the words. Git is not a backup and it is not a sync service. Dropbox and its equivalents keep the current state of a folder and quietly overwrite what was there before. Git keeps a chain of deliberate snapshots, each one labelled by a person, and never overwrites an earlier one.

That difference is the whole reason a research project wants it: “when did this figure change, and what else changed at the same time?” is answerable in one and not in the other.

You do not have to get good at this

Keeping a repository tidy is one of the things a coding agent is genuinely good at — better than most people are in their first year, and it is unglamorous work that it does not mind doing. Setting up the remote, writing commit notes that say what actually changed, a sensible .gitignore, noticing the file that should not be going up, splitting one sprawling change into commits that each make sense on their own, naming a branch after what it is for.

Once the credentials are in place, this is asked for in ordinary words. There is no syntax to learn. Real requests, in the form you would actually type them:

  • “Commit this, and write the note so it says what changed and why.”
  • “Set up a .gitignore for this project. Tell me what you excluded and why.”
  • “Is anything staged that should not be public?” Worth asking before every push for the first few weeks.
  • “Split what I just did into separate commits, one per thing.”
  • “What have I got that has not been pushed?”
  • “Summarise what changed in this project this week.” This is the one that makes a history worth keeping pay for itself.

What “credentials” means, per route

The one prerequisite. Until it is done the agent can read and commit but cannot send anything up, and the failure is a permissions error that does not explain itself.

  • Browser route — you connected your GitHub account when you picked the repository. That is it; it is already done. Cold Start W3.
  • Laptop or cluster route — signing in once per machine, usually with gh auth login, which opens a browser and hands the terminal a token. Cold Start 3.3. Once per machine, not once per project.

Do not paste a token or a password into a chat to fix this. If pushing fails for an authentication reason, the repair is to run the sign-in again, not to hand over a credential. A secret pasted into a session may end up in a log, in a commit, or in a file you did not know it wrote.

What stays yours

Delegating the mechanics is not the same as delegating the judgement, and this page would be arguing against the rest of the course if it pretended otherwise. Three things do not transfer:

  • Reading the diff before it becomes a commit The agent decides what to change; you decide whether that is what you wanted. A commit is where a change stops being easy to reverse.
  • Knowing whether the note is true It will write a fluent note describing what it believes it did. That is a different thing from what it did, and you are the only one in a position to notice the gap.
  • Deciding what must never be committed Participant data, a key, an unpublished result. The agent does not know which of your files those are unless you tell it — and once something is in the history, taking it out is a real job.

So the reason to read the next section is not that you will be typing these commands. It is that you will be reading them in a report, and approving them.

The words

Roughly a dozen, and they are the ones the other sheets use. If you can read these, you can read what your agent tells you it did.

repository · repo
A folder that git is watching, plus the entire history of that folder. When it lives on github.com rather than on your laptop, people still call it a repository. The two words mean the same thing. “Repo” is just the short form, and you will see both in the same paragraph.
commit
One saved version, with a short note attached saying what changed. Both a noun and a verb: you commit your changes, and the result is a commit. The note is the point. A commit whose note says “updates” is a version you will never find again. This is the one place where a habit of yours beats any software.
push · pull
Push sends your commits up to the copy on github.com. Pull brings down commits somebody else — or you, on another machine — put there. A commit that has not been pushed exists on exactly one machine. That is the failure Cold Start’s step 1.2 is about.
remote
The other copy: the one on github.com that push and pull talk to. Most projects have exactly one, and it is conventionally named origin. “Add a remote” means “tell this folder where its copy on the internet lives.” Until you have, push has nowhere to go.
clone
Making your own copy of a repository that already exists somewhere, with all of its history. This is how a project gets onto a second computer.
diff
A before-and-after view of exactly which lines changed. Red for gone, green for added, usually. This is the thing to actually look at. When an agent says it changed a file, the diff is the evidence and the sentence is not.
branch · main
A separate line of versions, so you can try something without disturbing the working one. main is the name of the default branch — the one you are on if nobody told you otherwise. You can go a long way using only main, and most people starting out should. Branching is on the list of things this page does not teach.
merge conflict
What happens when two sets of changes touch the same lines and git will not guess which one you meant. It stops and asks. It is not damage and nothing is lost. It is the one moment git refuses to be automatic, and it feels alarming the first time precisely because everything else was silent.
README
A plain text file describing what the thing is. Every repository is expected to have one, and github.com shows it on the front page.
.gitignore
A list of things git should not watch — scratch output, huge data files, anything with a password in it. Worth setting up early. A large file committed once stays in the history even after you delete it, which is a genuinely annoying thing to undo.
history · log
The chain of commits, oldest to newest. git log prints it. This is the thing all the rest is for. Cold Start step 5.1 asks whether you could say what your last three commits did — that question is asking whether your history is worth having.

The four things you will actually do

On the browser route you will not type any of these — you will ask for them in words and the agent runs them. They are here so that you recognise them when they go past.

  1. Look at what changed. git status — what is different since the last commit. Ask for it as: “what has changed since the last commit?”
  2. Save a version, with a note. git add then git commit. Ask for it as: “commit this, and say in the note what it does.”
  3. Send it up. git push. Ask for it as: “push this.” Or just “commit and push this” for both at once, which is what Cold Start W4 tells you to type.
  4. Read the history back. git log. Ask for it as: “what were the last five commits and what did each one do?”

Two commands are worth typing yourself even if you never type any others, because they only read and cannot break anything: git status and git log. Everything else in this list changes something.

What goes wrong, in order of how often

  • Committing but never pushing The work is saved and still on one machine. Nothing warns you, and you find out on the day that machine is not available.
  • Notes that say nothing “updates”, “fixes”, “wip”. The history exists and is unreadable, which costs you exactly when you need it.
  • Committing something that should not be public A key, a password, a participant list. Deleting it later does not remove it from the history — Cold Start is on a repository that has this problem on purpose, and says so.
  • Letting the agent commit without reading the diff It will do more than you asked sometimes, and the commit is where that becomes permanent. Reading the diff is the check.

What this page leaves out

Most of git. Named here so you know the shape of the hole rather than finding it at a bad moment:

  • Undoing things — revert, reset, restore, and the difference between them, which is the single most common thing people search for This is the clearest case for handing it over: describe the state you want to get back to, in words, and ask it to explain what the command will do before it runs. The commands are unforgiving and the explanations are cheap.
  • Branching and merging as a way of working — the whole topic, beyond the one-line definition above
  • Pull requests, review, and working with other people’s repositories — forks, review comments, everything social
  • Resolving a merge conflict — what to actually do when you are in one
  • Large files and data — Git LFS, and why putting a 4 GB file in a repository is a decision you cannot easily reverse
  • Anything about how git works underneath — the object store, hashes, what a commit really is. Genuinely interesting and not needed today.

There is no point at which this page becomes enough. It was written to cover one vocabulary, and it will still cover exactly that vocabulary after you have outgrown it. The list below is not a nice-to-have appendix; it is where this sheet stops.

Where to go instead

All free, all better than this page at what they do. In the order worth trying if you are coming from research rather than from software.

  • Start here · hands-on, for researchers Software Carpentry — Version Control with Git A worked lesson written for scientists, not developers, and used in workshops worldwide. If you do one thing on this list, do this one.
  • The research framing The Turing Way — Version Control Why version control matters for reproducibility, rather than how to drive it. Good for deciding what your group should do.
  • The book, when you want the real thing Pro Git Chacon and Straub, free in full online. The canonical explanation. Chapters 1–3 are the ones that matter first.
  • When you are stuck at a keyboard Oh Shit, Git!?! A short list of “I have done something bad, how do I get out of it.” Exactly the page you want at the moment you want it. Same content, milder title, at dangitgit.com.
  • The reference git-scm — the command reference Every command, exhaustively. Not for reading; for looking one thing up.
  • GitHub specifically GitHub Docs — Get started The website half rather than the git half: accounts, repositories, pull requests, Pages.
