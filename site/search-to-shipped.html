Search to Shipped

Zero to a deployed web app, for a researcher who has never written software. Every step, in order, with the condition that tells you it worked.

Version 0.1.4 · 29 Aug 2026First published 27 Aug 2026

Search

Returns links. You do the work.

Chat

Returns text. You decide what to do with it.

Agent

Changes files on your disk. That is the leap, and it is the only one that matters.

Why every step has a “done when”. An action and its report are two different events. A tool that says it worked is telling you it reached the end of its own instructions — not that anything happened. Check the world, not the summary. That habit is the entire skill; the steps are just where you practice it.

Phase 0 · Decide

5 min
  1. 0.1

    Answer two questions before anything else.

    One machine or several? Working alone or with others? Both answers change what you have to set up — and they are cheap now, expensive in week three.

    Several machines or any collaborators means a remote is mandatory, not optional. Skip ahead knowing that.

  2. 0.2

    Decide where data lives, before the first file exists.

    Synced storage (Dropbox, Box, OneDrive) keeps a copy on every machine — fast, quota-limited. Network research storage is mounted, not copied — one set of bytes everyone reads across the network. Pick which holds what.

    You can say, in one sentence, what goes where and why. Write it down; you will forget.

  3. 0.3

    Skip institutional storage and computing clusters unless you need them.

    You need them at terabyte scale, or for runs that would pin a laptop for hours. Both take days-to-weeks because someone else has to approve them — so if you do need them, request them today and carry on with the rest.

    Either the request is filed, or you have decided out loud that you do not need one.

Phase 1 · Set up

about an hour, once
  1. 1

    Make a GitHub account, then install and authenticate the GitHub CLI.

    gh auth login

    gh auth status prints your username.

  2. 2

    Install VS Code, git, and Node.

    git --version and node --version both answer in a terminal.

  3. 3

    Stop the machine sleeping through your own work.

    An agent session or an analysis run that outlasts your attention dies when the display sleeps or the lid closes — and it dies without a result, hours in. On a Mac, Amphetamine is free on the App Store and handles triggers and a closed lid; caffeinate -dimsu is already installed and needs nothing. Windows has PowerToys Awake, Linux systemd-inhibit.

    This is phase 0's cheap alternative and it belongs before the request. Phase 0 says ask for a cluster when a run would pin a workstation for hours. Plenty of those people do not need a cluster — they need the lid to stop killing the job. One costs a minute; the other takes weeks and someone else's approval.

    A run survives the screen going dark and the lid closing. Test it on something short before you trust it with something long.

  4. 4

    Get a coding-agent plan and install the extension.

    Check what your institution already provides before paying — many give staff API access against a billing code, and some give students a free chat tool that is not an agent. The difference is the whole point.

    The agent opens inside VS Code and answers a question about a file in your folder.

  5. 5

    Create the repository and add the remote in the same sitting.

    mkdir myproject && cd myproject && git init
gh repo create myproject --private --source=. --remote=origin
git commit --allow-empty -m "start"
git push -u origin main

    Adding the remote later is the single most common way a week of work ends up on one dead laptop.

    The repository is visible on github.com in a browser, not just in your terminal.

  6. 6

    Write a deny list before the first real task.

    A scratch folder is not a wall — the agent can leave it with an absolute path while doing exactly what you asked. A deny list is different in kind: the tool refuses the command instead of asking the model nicely. Start with rm -rf, sudo, git push --force, git reset --hard. See settings.

    You ask it to run a denied command and it refuses. Test this. An untested guard is a guess.

  7. 7

    Copy the data you need into the project. Never point the agent at the original.

    Containment by absence beats containment by permission. Every wall has to be right about every route out; an original that was never in the room cannot be damaged by any of them.

    Deleting your whole project folder would cost you a re-copy and nothing else.

Phase 2 · Know three things

2 min, read once
  • It will be confidently wrong, fluently, at any moment. Not occasionally and not with a warning. Everything can look right and be completely wrong. The skill is not avoiding this — it is catching it.
  • Context is a filling room, not a memory. It knows what has been put in front of it this session. A file it never opened may as well not exist — and rather than say so, it will fill the gap with something plausible. Point it at the file instead of describing the file.
  • A long session is not an accomplishment. The room fills, old instructions lose weight, and it starts contradicting a rule you set an hour ago. The tell is a mistake you already fixed together coming back. Start a fresh session; that is what the repo is for.

Phase 3 · Build

one afternoon
  1. 8

    Say the whole thing in one sentence.

    “A web page that shows my recordings one at a time and lets me mark the bad ones.” If you cannot say it in a sentence, you are not ready to ask for it.

    Someone outside your field understands what it does.

  2. 9

    Break it into parts. Break each part into elements.

    This decomposition is the actual skill. Not prompt wording — there is no secret phrasing, and sculpting one is a stage people pass through and leave behind.

    You have a list where every item is one afternoon or less.

  3. 10

    Do one element. Never two.

    The temptation is to start a second thing while it works. Resist it until you have done this twenty times. You need the focus for spec, structure, and spotting the failure.

    You can name, in one line, the single change that just happened.

  4. 11

    Check it four ways. None of them needs you to read code.

    Read the diff for scope, not correctness — what did it touch that you did not ask about? Run it and look. List the files that now exist. Open the artifact yourself.

    You have seen the thing work, not read a message saying it does.

  5. 12

    Commit, then push.

    git add -A
git commit -m "what changed and why"
git push

    Committing is not pushing. An unpushed commit exists on exactly one machine and reaches nobody, including you tomorrow on a different one.

    The change is visible on github.com.

  6. 13

    Re-spec, and expect to.

    Seeing it built is what tells you what you actually wanted. Revising the spec is the normal case, not a failure — it is the loop working.

    The next element is described more precisely than the last one was.

↻ Repeat 9 → 12 until it does what the sentence in step 7 said.

Phase 4 · Write down why

10 min, per real decision
  1. 14

    Every time you choose between two real options, record the decision before you forget the reasoning.

    One small file per choice, in the repo, numbered and dated. This is the single highest-value habit on the page and it is the one everybody skips, because at the moment you make a decision the reasoning feels unforgettable. It is not. In six weeks you will find a strange-looking choice in your own project and have no idea whether it was careful or careless.

    decisions/0003-one-file-per-recording.md

Date: 2026-08-27   Status: accepted

What we chose:    one file per recording, not one big table.
What we rejected: a single combined file — simpler to load, but
                  every re-export rewrites all of it.
Why:              re-exports happen weekly; whole-file rewrites
                  cost an hour and risk the lot.
Revisit if:       recordings drop below ~20, or exports stop.

    Someone who was not there — including a fresh agent session tomorrow — can read it and not reopen the argument.

  2. 15

    Never edit one. When a decision reverses, write a new record saying it supersedes the old.

    The old record stays, wrong, on purpose. A series you can quietly rewrite is not a record of anything — you would only ever see the decisions that happened to survive, which tells you nothing about whether any of them could have failed.

    Your decisions/ folder contains at least one record that is no longer true and says so.

Why this beats telling the agent to remember. An agent starts every session with no memory of last week’s debate, so an unrecorded decision gets relitigated — at best wasting a session, at worst quietly reversed while you are not looking. And a decision record cannot go stale the way documentation does: it describes a choice made on a date, not a state of the world, so it stays true even after the decision is overturned. Point the agent at the folder.

Phase 5 · Ship

20 min
  1. 16

    Put it on the internet.

    A static site — one built from your files with no server of its own — is enough for most research tools and is free to host. GitHub Pages is the shortest path from a repo you already have. Cloudflare Pages and Vercel add a custom domain easily. Ask the agent to set up Vite if you need a build step.

    The URL loads on your phone, off your wifi.

  2. 17

    Send it to one person who was not involved.

    You cannot see your own assumptions. They will hit the broken thing in ninety seconds.

    They used it without you narrating.

Phase 6 · What will bite you

ongoing
  • Jargon Its reply is your only evidence of how it understood you. It comes back in words you do not know. Ask for plain language, then actually read the answer — skipping it and assuming the work is right because the explanation sounded right is how a small mistake grows past the point where anything can contain it.
  • Silence Five ways it goes wrong; two of them do not announce themselves. Wrong output, right output in the wrong place, and silently doing nothing all show up eventually. Doing more than you asked, and reporting a success it never achieved, do not. Those two are why step 10 exists.
  • Requests A request is not a rule. Instruction files are advisory, and the second sentence still gets skipped no matter how you word it. Worse, config files often look executable and are not — a declared setting that nothing reads is a note wearing a mechanism’s clothes. Ask what enforces it. If nothing does, it is a habit.
  • Staleness Documentation was true when written and says nothing about the difference. Including official pages, including yours, including what you told the agent to remember last month. When two documents disagree, they can only disagree — stop reading and go touch the actual system. That third check is the only one that cannot be out of date.
  • Memory “Remember this” is a trap. Telling it to remember a hard-won correction manufactures a document that starts aging immediately, undated, that nobody re-reads. What lasts is a check something runs, or a dated decision record (phase 4) — which cannot go stale, because it never claimed to describe the present.
  • Asymptote Two ways to never finish. The guarding becomes the work — a beautiful setup script will not analyze your data. And the work itself is never perfect; the app can always be better. Both are legitimate, which is exactly what makes them hard to stop.

Phase 7 · Habits that hold

from day one
  • Keep a friction log in the repo. One line, today, about something that just annoyed you. Repetition is the signal — the third time is when you build the cure.
  • Cures come in three kinds, and only one is a tool. A tool, a change of habit, or a check you accept forever. Not every fix is tool-shaped, and a cure that is expensive to use silently stops being used.
  • Stop a session on purpose, before it degrades. Not when it falls apart. You choose the moment.
  • Never end without a handoff — committed. What you did, what is next, what is unfinished. A note that only exists in a session that has closed never existed at all.

What this is actually about

Communication

You speak plainly and it understands. It answers in jargon, and that answer is your only evidence.

Idiosyncrasies

Your setup has quirks — which machine, which path, where the data is. It inherits them silently and nothing crashes.

Validation

Everything can look right and be totally wrong. Spec, validate, re-spec.

The asymptote

Guarding is absorbing and the work is never perfect. Knowing when to stop is a skill of its own.

Coding is no longer the barrier. These four are — and none of them is solved by writing a better prompt.

Sheet two · expands phase 4

Decision Records

One small file per choice, kept in the repo forever. The cheapest thing you will ever do, and the one you will most regret skipping.

When to write one

the whole difficulty

Write one

  • You chose between two real options. Both were defensible. That is what makes it a decision rather than a step.
  • You decided not to do something. The most valuable records, because nothing in the repo shows the road not taken. Six months on, the absence looks like an oversight.
  • You reversed an earlier choice. New record, pointing at the old one. Never a quiet edit.
  • You settled an argument you do not want again. Some records exist only to say: this was reconciled, do not relitigate.

Do not

  • What you did today. That is a handoff or a friction log entry.
  • How the system works. That is documentation. It describes the present and will go stale; a record describes a moment and cannot.
  • Something you still have to do. That is a task. Records are closed by construction.
  • Anything with no rejected alternative. If nothing was turned down, no decision was made — you are writing a note and filing it in the wrong place.

The file

ten lines is plenty 
decisions/0007-drop-frames-before-alignment.md

# 0007 · Drop bad frames before alignment, not after

Date:   2026-08-27
Status: accepted        (proposed | accepted | superseded by NNNN)

## Decision
Discard frames failing the quality check before the alignment step.

## Rejected
Align everything, then discard. Simpler code, one pass — but a bad
frame drags the alignment for its neighbours, so discarding after
leaves damage behind that nothing downstream can see.

## Why it went this way
Tested both on 20260811_375. Post-alignment discard left a 3 px
drift in the surrounding 40 frames. Pre-alignment did not.

## Revisit if
The quality check gets strict enough to drop >10% of frames, or
alignment stops being sensitive to neighbours.

Every section earns its place. Rejected is what makes it a record and not a note. Revisit if is what stops it becoming dogma — it names, in advance, the evidence that would overturn it.

Six rules

all of them cheap
  1. 1

    Append-only. Never edit a landed record.

    When a decision reverses, write a new record that says what it supersedes, and add Status: superseded by 0011 to the old one — that status line is the only edit ever permitted. Memory you can silently rewrite is not memory: you would only ever see the decisions that happened to survive.

  2. 2

    Date every record, and never backdate one.

    The date is what makes the record immune to going stale. It does not claim the decision is still right — only that it was made, then, for these reasons.

  3. 3

    Write the rejected option in as much detail as the chosen one.

    A record that only argues for what you did cannot fail, and a check that cannot fail is not a check. The rejected option is also what a future reader is actually reaching for, because it is the thing they are about to propose.

  4. 4

    Cite records by full filename, never by bare number.

    Numbers collide as soon as more than one line of work is running. Filenames do not, and a citation that reads 0005-coordination-export-contract.md tells the reader what it is without opening it.

  5. 5

    Allocate the number when you commit, and never fill a gap.

    Not when you start writing. Two parallel sessions each take “the next number after the highest I can see”, and what each can see is its own branch — the sequence then has one integer meaning two unrelated things. Refusing to backfill keeps numbering monotonic in time, so the sequence doubles as a chronology.

    Solo on one machine, this costs nothing and you will never notice it. The first day it matters, it will already have been free for a year.

  6. 6

    Graduate the important ones into something that fires.

    A hazard is not handled when it is written down; it is handled when something refuses without anyone remembering why. Turn the record into a check — a test, a guard, a name that makes the wrong thing impossible to express — and cite the record from the failure message, so whoever trips it gets the reasoning and not just a refusal.

What it buys you

  • The agent has no memory of last week’s debate. Every session starts cold. An unrecorded decision gets relitigated — a wasted session at best, quietly reversed at worst, while you are looking somewhere else. This folder is what you point it at.
  • Future you finds a strange choice and cannot tell if it was careful. This is the common case and it is worse than it sounds, because the honest response to an unexplained choice is to leave it alone — so a careless decision and a hard-won one become equally permanent.
  • Someone asks why, and you have an answer instead of a memory. A reviewer, a collaborator, a committee, or a reader of the paper. The record was written when you still knew, which is the only time anyone ever does.

Start now, badly. Make decisions/ and write one record today about a choice you already made — from memory, marked as reconstructed. Four sections, ten lines. A thin series that exists beats a rigorous one you were going to start when the project got serious, and the project will not announce when that happens.
